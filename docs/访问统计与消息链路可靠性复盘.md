# 访问统计与消息链路可靠性复盘

## 1. 复盘范围

当前短链接访问链路由三部分组成：

1. 跳转请求访问 Redis，并把访问次数累加到 `short-link:visit:{shortCode}`。
2. 跳转请求发布 RabbitMQ 访问事件，由消费者写入访问事件去重表和每日 PV 表。
3. 定时任务把 Redis 中的访问增量同步到 `short_link.visit_count`。

这条链路的目标不是追求“任何情况下绝对不重复”，而是先保证访问量不因单点故障永久丢失，再通过幂等设计逐步逼近 exactly-once。

## 3. 重点问题复盘

### 3.1 定时同步的 at-most-once 问题

旧流程如下：

```text
Redis getAndDelete
        ↓
MySQL increment
        ↓
写库失败：计数已经从 Redis 消失
```

失败原因包括数据库连接中断、SQL 异常、返回 0 行，以及进程在两步之间崩溃。无论哪一种情况，已经删除的增量都无法自动恢复。

当前实现改为：

```text
Lua 原子领取：pending → processing
        ↓
MySQL increment
        ├─ 临时失败：processing 原子合并回 pending
        ├─ 返回 0 行：移动到 orphan key，等待人工处理
        ├─ 计数格式非法：移动到 corrupt key
        └─ 写库成功：删除 processing key
```

处理中 key 超过 5 分钟没有完成时，下一轮扫描会尝试恢复。领取期间新产生的访问继续写入 pending key，不会覆盖已领取的批次。

这里采用的是 at-least-once，而不是 exactly-once。比如 MySQL 已经成功，但 Redis 删除 processing key 时发生故障，后续恢复可能重复写入同一批次。要进一步解决重复问题，需要给同步批次增加唯一 ID，并在 MySQL 中建立批次幂等记录或使用可重放的明细表。

### 3.2 DLQ 为什么不能只声明不消费

死信队列只能保存失败消息，不能自动完成业务处理。没有消费者时，消息会持续堆积，最终只能人工登录 RabbitMQ 管理台查看。

实际业务至少需要明确一种策略：

- 自动重试后进入 DLQ，人工确认原因后重放；
- 对确定不可恢复的消息记录告警并丢弃；
- 对临时依赖故障的消息延迟重试，避免立即打满消费者。

DLQ 消费者不能简单地“收到后直接重新发送”，否则可能形成死循环。必须限制重试次数，并记录原始异常原因。

### 3.3 publisher confirm 与 returns 的区别

两者解决的问题不同：

- publisher confirm：RabbitMQ 是否接受了消息并写入交换机流程；
- publisher returns：消息已经到达交换机，但没有匹配到任何队列；
- mandatory：要求不可路由消息触发 returns，而不是被静默丢弃。

因此只配置 confirm 仍然不够。生产者至少要记录消息 ID、短码、交换机、路由键和失败原因，必要时把未确认消息写入本地补偿表。

### 3.4 缓存命中为什么仍需要状态校验

当前 Redis 命中只返回 URL 和短链接 ID，缓存对象没有 `status`。如果数据库中的短链接后来被禁用，而 Redis 删除失败，命中分支仍会直接跳转。

常见处理方式有三种：

1. 缓存值同时保存 `status` 和 `expireAt`，命中时本地校验；
2. 缓存只保存 ID，命中后回查状态，牺牲一部分性能换一致性；
3. 使用版本号或短 TTL，配合可靠失效消息降低窗口。

本项目当前更适合第一种，并保留 Redis 故障时回源 MySQL 的降级路径。

### 3.5 缓存穿透与负缓存

攻击者可以反复访问不存在的短码。如果不存在结果不缓存，每次请求都会查询 MySQL。

负缓存只需要保存一个短 TTL 标记，例如 30 秒到 1 分钟。写入负缓存时要注意：

- 短码格式非法时不必写缓存；
- 管理员刚创建同一短码后，创建流程需要删除负缓存；
- 负缓存 TTL 不能过长，避免真实创建后仍然返回不存在。

### 3.6 时间模型

`LocalDateTime` 只表示“墙上时间”，不包含时区和偏移。跨时区部署时，同一个瞬间可能被不同节点解释成不同日期。

更稳妥的方案是：

- 事件消息使用 `Instant` 或带偏移的 `OffsetDateTime`；
- 数据库统一使用 UTC 存储；
- 统计报表按工作空间配置的时区转换日期。

### 3.7 旧接口与租户边界

旧 `/api/links` 创建接口不携带工作空间，无法保证数据归属；旧统计接口使用 `X-Manage-Token`，与 JWT + workspace member 的新权限模型不一致。

迁移时不能简单放宽 `workspace_id` 非空约束。正确顺序是：

1. 前端切换到 `/api/v1/workspaces/{workspaceId}/links`；
2. 监控旧接口调用量；
3. 返回弃用提示；
4. 最后下线旧接口。

## 4. 面试问答准备

### 问：为什么 `getAndDelete` 会导致访问量丢失？

答：它把 Redis 删除和 MySQL 写入拆成了两个步骤。删除成功后进程可能在数据库写入前崩溃，或者数据库返回 0 行、连接异常，此时 Redis 中已经没有原始增量，因此属于 at-most-once。现在先转移到 processing key，失败时再合并回 pending key，改成 at-least-once。

### 问：为什么不直接使用 Redis `get`，写库成功后再 `delete`？

答：并发访问期间可能有新增量写入。如果直接删除，可能把新计数一起删掉；如果先读后删，还会遇到进程崩溃导致重复或丢失。Lua 脚本可以在 Redis 内原子领取，并让新访问继续写入新的 pending key。

### 问：你们实现的是 exactly-once 吗？

答：当前是 at-least-once。它优先保证不丢计数，但在数据库成功、Redis 确认失败的窗口可能重复。若需要 exactly-once，需要同步批次 ID、数据库唯一约束和幂等落库记录，不能仅靠 Redis 删除顺序保证。

### 问：publisher confirm 和事务消息有什么区别？

答：publisher confirm 只确认 RabbitMQ 是否接收消息，不能保证消费者已经处理，也不解决消息不可路由。事务消息或本地消息表可以把业务数据库提交和消息补偿关联起来，但成本更高，应根据一致性要求选择。

### 问：为什么要有 DLQ？

答：DLQ 把持续失败的消息从主队列隔离出来，避免阻塞正常消息，同时保留排查和重放入口。它不是自动修复机制，仍需要重试次数、告警和人工处理策略。

### 问：缓存删除失败时如何保证禁用短链立即生效？

答：缓存命中路径不能只信任 URL，应缓存状态并校验 `ACTIVE`；同时缩短 TTL、增加可靠失效通知，必要时对高风险操作回查数据库。当前系统还需要补上这层状态校验。

### 问：为什么要使用负缓存？

答：公开短码容易被扫描，不存在短码如果每次都查数据库会形成缓存穿透。负缓存用短 TTL 记录“不存在”，可以保护数据库；创建同名短码时必须主动删除该负缓存。

### 问：为什么不直接使用 `LocalDateTime`？

答：它没有时区信息，适合单时区本地业务，不适合跨时区事件链路。事件应使用 `Instant`，展示或统计时再按业务时区转换。

### 问：为什么 Redis key 要带环境前缀？

答：多个环境共用 Redis 实例时，固定前缀会导致开发、测试、生产互相覆盖。环境前缀能隔离数据，例如 `short-link:dev:`、`short-link:test:`。

## 8. 实习项目范围与生产增强备忘

本项目定位是可运行、可测试、可解释的 Java 后端实习项目，不把所有生产级能力一次性堆进第一版。以下能力暂不实现，但保留面试时的处理方案：

| 暂缓能力 | 生产环境的处理方式 | 当前暂缓原因 |
| --- | --- | --- |
| Outbox 事务消息 | 在业务事务中写入本地消息表，由后台任务可靠投递并重试 | 每次访问写 MySQL 会增加跳转链路和数据库压力 |
| exactly-once | 使用事件 ID、幂等批次表和唯一约束，把重复执行变成安全重试 | 当前 at-least-once 已能覆盖实习项目的主要故障窗口 |
| DLQ 自动重放平台 | DLQ 保留消息，配合告警、人工审核和修复后的定向重放 | 业务量和运维规模不足以支撑独立重放平台 |
| 分布式链路追踪 | 接入 OpenTelemetry/TraceId，贯穿 HTTP、Redis、RabbitMQ 和 MySQL | 当前先用请求日志和事件 ID 定位问题 |
| Prometheus/Grafana 监控 | 采集发布确认、消费失败、DLQ 堆积、Redis 降级和同步延迟指标 | 当前先保留关键日志与 RabbitMQ 控制台检查 |
| 多环境 Redis Key 隔离 | 配置化环境前缀，例如 `short-link:dev:`、`short-link:test:` | 当前各环境使用独立本地实例，先记录风险 |
| 全部时间字段改为带时区类型 | 事件用 `Instant`/`OffsetDateTime`，数据库统一 UTC，报表按工作空间时区转换 | 当前部署假设为单时区，避免扩大迁移范围 |
| 旧接口立即下线 | 先统计调用量、增加弃用提示，再切换前端并最终下线 | 保留兼容接口便于现有联调，不放宽新工作空间权限边界 |
| 高并发压测和容量评估 | 使用压测数据确定 Redis、RabbitMQ、MySQL 的吞吐和告警阈值 | 当前没有稳定的部署环境和容量目标，不能虚构性能数据 |

面试时应明确说明：当前方案追求“核心链路可用、故障可降级、消息可追踪、重复可幂等”，没有声称绝对不丢或 exactly-once；如果业务一致性等级提高，再按上表逐项演进。
