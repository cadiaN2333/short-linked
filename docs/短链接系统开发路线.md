# 短链接系统开发路线

> 文档使用说明：第 1～9 节保留设计原则、接口契约和面试复盘素材；其中“从零搭建顺序”和早期 MVP 示例属于历史过程，不代表当前代码仍按该顺序执行。当前可执行状态以第 10～12 节和最新过程记录为准。

## 1. 项目定位

本项目用于从零实现一个可运行、可测试、可逐步扩展的短链接 SaaS 后端。开发阶段以“后端代码自己手敲、边做边学”为原则，第一版采用模块化单体架构，优先掌握完整请求链路、数据库设计、异常处理和测试方法；不引入微服务、支付或没有实际需求支撑的复杂分布式组件。Redis 和 RabbitMQ 只在基础跳转闭环验证后，按明确的故障边界和测试结果逐步引入。

项目最终可以作为 Java 后端实习简历项目，但简历中的技术描述和性能数据必须以实际完成的功能、测试记录及压测结果为准。

## 2. 技术路线

- Java 17 或更高的长期支持版本
- 当前稳定维护的 Spring Boot 版本
- Spring Web：提供 HTTP 接口和重定向能力
- Validation：校验接口请求参数
- MyBatis 或 MyBatis-Plus：访问数据库，建议第一版使用 MyBatis-Plus 减少模板代码，同时手写关键 SQL 以理解执行过程
- MySQL：持久化短码、原始链接和有效期
- Flyway：管理数据库版本迁移，替代手工执行建表和改表脚本
- Redis：基础版完成后再作为缓存引入
- Maven：管理依赖和构建项目
- Postman：手动验证接口
- JUnit、Mockito 和 Spring Boot Test：编写自动化测试

## 3. MVP 基础闭环

第一阶段只实现以下完整闭环：

1. 用户提交原始 URL。
2. 服务生成唯一短码并保存到 MySQL。
3. 服务向用户返回可访问的短链接。
4. 用户访问短链接时，服务查询原始 URL。
5. 链接存在且未过期时返回 HTTP 302 重定向。
6. 链接不存在或已经过期时返回明确的错误响应。

基础闭环阶段曾不实现用户系统、前端页面、访问统计、分库分表和微服务；该阶段已经完成，当前项目已进入认证、工作空间和异步访问统计阶段。

### 3.1 MVP 验收标准

- 应用可以在本地稳定启动，并能连接 MySQL。
- `POST /api/v1/workspaces/{workspaceId}/links` 可以在当前用户有权限的工作空间内创建短链接。
- 旧的 `POST /api/links` 已不再属于有效契约，客户端不得继续调用。
- 数据库中可以查到对应的短码、原始 URL、创建时间和过期时间。
- `GET /{shortCode}` 可以对有效链接返回 302，并在 `Location` 响应头中携带原始 URL。
- 重复生成短码时能够通过数据库唯一约束发现冲突并重试。
- 非法 URL 返回 400，不写入数据库。
- 不存在或已过期的短码返回 404。
- 核心业务至少具有自动化测试，不能只依赖 Postman 手动验证。

### 3.2 当前第一阶段目标：异步访问统计与最近 7 天趋势

基础跳转闭环完成后，当前阶段增加 Redis 访问增量、RabbitMQ 访问事件和 MySQL 每日聚合统计。SaaS 管理接口已迁移到 JWT 与工作空间边界，供前端或 Apifox 直接联调：

```text
GET /api/v1/workspaces/{workspaceId}/links/{linkId}/analytics?granularity=day
Authorization: Bearer {accessToken}
```

旧的 `/api/links/{shortCode}/stats` + `X-Manage-Token` 暂作为兼容接口保留，后续完成调用方迁移后下线。

当前阶段验收规则：

- 未传日期时返回最近 7 个自然日，包含当天。
- `from`、`to` 形成闭区间；只传一个日期时自动补齐 7 天。
- 返回结果按日期升序排列，没有记录的日期返回 `pv=0`。
- 最大查询范围为 90 个自然日，第一版只支持 `granularity=day`。
- RabbitMQ 消费端以事件 ID 幂等，重复事件不得重复增加每日 PV。
- RabbitMQ 或 Redis 故障不能阻止有效短链接返回 302。
- `visitCount` 表示已同步的累计访问量，`pvTrend` 表示消息消费后的每日聚合量，两者允许短暂不一致。

## 4. 从零搭建顺序

### 第 1 步：建立项目骨架

使用 Spring Initializr 创建 Maven 项目，先添加 Spring Web、MySQL Driver、MyBatis 或 MyBatis-Plus、Validation 和测试相关依赖，暂不添加 Redis。

第一版可以按职责组织目录：

```text
controller   接口入口
service      业务逻辑
mapper       数据库访问
entity       数据库对象
dto          接口请求和响应对象
exception    业务异常和统一异常处理
config       项目配置
```

建议将请求 DTO、响应 DTO 和数据库实体分开，避免直接把数据库对象暴露给接口调用方。

### 第 2 步：连通应用和数据库

创建本地 MySQL 数据库，在 `application.yml` 中配置数据库连接。数据库账号和密码不要提交到 Git，可以通过环境变量或仅供本地使用且被 `.gitignore` 忽略的配置文件注入。

先实现应用健康检查，再通过一条简单查询验证数据库连接。健康检查接口与数据库检查可以分开，避免数据库短暂不可用时无法判断应用进程是否存活。

#### 2.1 数据库迁移管理约定

数据库结构统一由 Flyway 管理，迁移脚本放在 `src/main/resources/db/migration`，使用 `V1__...sql`、`V2__...sql` 的版本命名。当前已有数据库通过 `V1__baseline_schema.sql` 接管，保留既有数据；后续不再要求开发者手动执行 `docs/sql` 中的业务迁移脚本。

Flyway 配置启用非空数据库基线、迁移校验和禁用 clean。数据库连接失败、权限不足、端口占用等环境问题不通过修改业务代码规避，按启动日志完成本地环境处理即可。

### 第 3 步：设计最小数据表

第一版只需要一张短链接表：

```sql
CREATE TABLE short_link (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    short_code VARCHAR(16) NOT NULL COMMENT '短码',
    original_url VARCHAR(2048) NOT NULL COMMENT '原始链接',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    expire_at DATETIME NULL COMMENT '过期时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_short_code (short_code)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '短链接表';
```

关键设计说明：

- `short_code` 必须具有唯一索引，应用层生成随机值不能替代数据库约束。
- `original_url` 使用足够大的字段长度，避免常见长链接被截断。
- `expire_at` 允许为空，表示永久有效。
- 是否过期应由服务端当前时间与 `expire_at` 比较，不建议第一版通过定时任务删除数据。
- 建表 SQL 建议保存在项目的 `sql` 或 `db/migration` 目录中，确保其他人可以复现数据库结构。

### 第 4 步：实现创建短链接（历史过程）

接口示例：

```http
POST /api/links
Content-Type: application/json
```

请求示例：

```json
{
  "originalUrl": "https://example.com/articles/123",
  "expireAt": "2026-12-31T23:59:59"
}
```

响应示例：

```json
{
  "shortCode": "aB3x9K",
  "shortUrl": "http://localhost:8080/aB3x9K",
  "originalUrl": "https://example.com/articles/123",
  "expireAt": "2026-12-31T23:59:59"
}
```

建议的业务流程：

1. 校验 URL 是否为空、协议是否为 HTTP 或 HTTPS，以及过期时间是否晚于当前时间。
2. 使用明确的字符集生成固定长度随机短码。
3. 插入数据库。
4. 如果触发短码唯一键冲突，则重新生成并重试。
5. 达到最大重试次数后返回服务端错误并记录日志，避免无限循环。
6. 根据配置的服务域名拼装短链接，不在业务代码中写死 `localhost`。

初版不必对相同原始 URL 强制返回同一个短码。是否去重会影响过期时间、用户隔离和统计口径，适合在后续需求明确后再决定。

### 第 5 步：实现短链接跳转

用户访问：

```http
GET /{shortCode}
```

建议的处理流程：

1. 校验短码格式。
2. 根据短码查询数据库。
3. 记录不存在时返回 404。
4. `expire_at` 不为空且已到期时返回 404。
5. 有效时返回 302，并设置 `Location` 响应头。

302 适合第一版，因为浏览器不会像处理永久重定向那样长期缓存映射关系，后续修改目标地址或统计访问请求时更可控。

### 第 6 步：补充校验、异常处理和测试

至少覆盖以下情况：

- 正常创建短链接。
- 原始 URL 为空、格式错误或使用非 HTTP/HTTPS 协议。
- 过期时间早于当前时间。
- 短码发生唯一键冲突后成功重试。
- 有效短码正确返回 302。
- 不存在的短码返回 404。
- 过期短码返回 404。
- 数据库异常时返回统一错误结构，且不向调用方暴露堆栈或数据库信息。

测试建议分层进行：

- Service 单元测试：验证生成、重试和过期判断等核心逻辑。
- Mapper 集成测试：验证字段映射和 SQL。
- Controller 或端到端测试：验证状态码、响应体及重定向头。
- Postman 手动测试：作为演示和辅助验证，不替代自动化测试。

### 第 7 步：基础版稳定后引入 Redis

缓存映射关系：`shortCode → originalUrl`。跳转时先查 Redis，未命中再查 MySQL 并回填缓存。

引入 Redis 时需要同时考虑：

- 缓存过期时间不能晚于短链接自身的过期时间。
- 不存在的短码可能导致缓存穿透，可为无效短码设置较短的空值缓存。
- 修改或删除短链接时需要保证缓存与数据库最终一致。
- Redis 不可用时应降级查询 MySQL，不能让整个跳转服务直接失效。

## 5. 推荐的迭代顺序

### 里程碑一：可运行的基础版

- 创建短链接
- 302 跳转
- MySQL 持久化
- 参数校验和统一异常处理
- 核心自动化测试

### 里程碑二：工程质量

- OpenAPI 接口文档
- 数据库版本迁移工具
- Docker Compose 启动 MySQL 和应用
- 多环境配置与敏感信息隔离
- 结构化日志和请求追踪标识

### 里程碑三：性能优化

- Redis 缓存
- 缓存穿透保护
- 使用压测工具建立无缓存与有缓存的对照结果
- 记录吞吐量、平均响应时间、P95、P99、错误率和数据库查询次数

### 里程碑四：简历增强功能

按价值和学习成本从高到低选择，不必全部实现：

1. 访问统计：访问次数、最近访问时间、来源或按天聚合。
2. 限流：限制创建接口和异常高频访问，说明采用的算法及限制维度。
3. 幂等或防重复提交：避免客户端重试产生非预期的重复记录。
4. 自定义短码：处理格式校验、敏感词、保留路径和短码占用。
5. 批量创建：控制批量大小，并设计部分失败时的响应。
6. 链接管理：查询、禁用、修改过期时间，但需要先确定是否增加用户身份体系。

不建议为了“显得高级”而强行加入微服务、Kafka、分库分表或分布式事务。面试官通常会追问技术引入的实际问题、数据量和权衡，没有真实需求支撑的组件反而会增加解释风险。

## 9. 需要掌握的面试问题

完成项目时，应能够独立回答：

- 为什么使用 302，而不是 301、307 或 308？
- 随机短码使用什么字符集和长度，碰撞概率如何估算？
- 为什么应用层检查不能替代数据库唯一索引？
- 唯一键冲突为什么要限制重试次数？
- 如何判断 URL 合法，为什么只允许 HTTP 和 HTTPS？
- Redis 缓存使用什么数据结构，键和值如何设计？
- 如何处理缓存穿透、缓存击穿和缓存雪崩？
- Redis 故障后系统如何降级？
- 缓存与数据库不一致时如何处理？
- 压测环境、数据规模和指标如何记录，结果是否可复现？
- 如果访问量继续增长，系统中最先出现的瓶颈可能是什么？

## 10. 当前最优行动顺序

当前基础设施、Flyway、认证、工作空间、短链接生命周期和访问统计均已完成。后续以“修复会误导调用方的失效契约，再补高收益安全与一致性保护”为顺序：

1. 删除旧的 `POST /api/links` 创建入口及无工作空间创建重载；保留旧统计接口直到调用方迁移完成。
2. 将短链接基地址改为配置项，避免反向代理或异步场景返回内网地址/半截路径。
3. 登录成功时只更新 `last_login_at`，避免把用户全字段回写数据库。
4. 访问统计累加 SQL 增加 `status <> 'DELETED'` 条件。
5. 不修改已经执行过的 V3 迁移文件；通过文档记录其非原子历史，并约定后续结构变更使用新版本迁移脚本。
6. 后续按实习项目剩余时间评估登录限流、管理凭证哈希、关键词检索优化、时区统一和 Redis 环境隔离。

慢速 Maven 全量测试、MySQL/RabbitMQ/Redis 联调由用户在本机执行；端口、权限、凭据等环境问题只提供处理指引，不通过业务代码规避。
