# 短链接 SaaS 项目面试题与参考回答

本文基于当前项目真实代码整理。回答时应区分“当前已经实现的能力”和“生产环境的演进方案”，不要把规划中的功能描述成已经上线。

## 一、项目概述

### 1. 请用 3 分钟介绍这个项目

参考回答：

这是一个基于 Java 17、Spring Boot、MyBatis-Plus、MySQL、Redis 和 RabbitMQ 实现的短链接 SaaS 后端。项目采用模块化单体架构，主要包含用户认证、JWT、工作空间、多租户权限、短链接生命周期管理、Redis 跳转缓存、RabbitMQ 访问事件和访问统计等模块。

用户注册后会自动创建个人工作空间。短链接创建、查询、修改和统计都必须经过 JWT 和工作空间成员关系校验。公开跳转链路优先从 Redis 查询，访问次数写入 Redis，访问事件发送到 RabbitMQ，消费者异步更新每日 PV，定时任务再把 Redis 增量同步到 MySQL。

项目重点不在堆砌组件，而在于保证核心链路可用、缓存和消息故障可降级、统计重复消费可幂等，并通过 Flyway 管理数据库迁移。

### 2. 为什么采用模块化单体，而不是微服务？

参考回答：

当前项目规模和团队规模较小，模块化单体可以保留清晰的领域边界，同时减少服务发现、分布式事务、部署和链路追踪成本。后续如果访问量或团队规模增长，可以按认证、短链接、统计等边界拆分服务，但目前没有必要为了形式引入微服务。

### 3. 项目的核心请求链路是什么？

参考回答：

管理链路是“JWT 认证 → 工作空间成员校验 → 短链接业务操作 → MySQL 持久化”。公开跳转链路是“短码请求 → Redis 查询 → 缓存未命中时查询 MySQL → 返回 302 → Redis 记录访问次数 → RabbitMQ 发布访问事件”。统计链路则由 RabbitMQ 消费者和定时同步任务异步完成。

## 二、短链接设计

### 4. 短码如何生成？为什么使用 Base62？

参考回答：

系统使用数字、大写字母和小写字母组成 Base62 字符集，随机生成固定长度短码。Base62 在较短字符串中可以表达较多组合，适合 URL 场景。应用层生成只负责提供候选值，最终仍依赖数据库唯一索引保证正确性。

### 5. 短码冲突如何处理？

参考回答：

数据库 `short_code` 上有唯一索引。插入时如果发生唯一键冲突，随机短码会在限定次数内重新生成；自定义短码冲突则直接返回明确的冲突错误，避免无限重试。

### 6. 为什么使用 302 跳转？

参考回答：

302 更适合第一版短链接服务。它不会像 301 那样被浏览器和代理长期缓存，修改目标地址、禁用链接和统计访问时更容易保持可控。未来如果业务明确要求永久跳转，再评估 301、307 或 308。

### 7. 为什么设计 ACTIVE、DISABLED、DELETED 三种状态？

参考回答：

`ACTIVE` 表示可以公开跳转，`DISABLED` 表示暂时停止跳转但保留数据，`DELETED` 表示软删除。这样既能满足运营启停，也能保留统计和审计信息。公开跳转只允许 ACTIVE，管理列表和详情会排除 DELETED。

### 8. 自定义短码有哪些校验？

参考回答：

当前限制长度为 3 到 16，只允许数字、字母、下划线和连字符，同时拦截 `api`、`actuator`、`error`、`swagger-ui`、`v3` 等系统保留路径。数据库唯一索引负责处理并发冲突。

## 三、SaaS 与工作空间

### 9. 用户、工作空间和成员关系是什么？

参考回答：

用户通过 `workspace_member` 参与工作空间，成员关系包含角色；工作空间保存拥有者和状态；短链接通过 `workspace_id` 归属到具体工作空间。注册事务会创建个人工作空间，并写入 OWNER 成员关系。

### 10. 如何防止跨工作空间访问？

参考回答：

控制器先从 JWT 的 `sub` 获取当前用户，再由 `WorkspaceAccessService` 校验成员关系。短链接查询、修改、删除和统计还会在 SQL 中携带 `workspace_id`，形成“用户身份、工作空间成员、资源归属”三层校验，不能只依赖前端传入的工作空间 ID。

### 11. 当前一个用户只能有一个工作空间，合理吗？

参考回答：

当前项目定位是个人工作空间实习项目，所以使用 `owner_user_id` 唯一索引简化模型。若以后支持一个用户拥有多个工作空间，应通过新的 Flyway 迁移删除该唯一索引，并增加明确的所有权和角色约束，不能直接修改已经执行过的迁移脚本。

## 四、Redis 与缓存

### 12. Redis 在项目中承担什么职责？

参考回答：

Redis 主要承担短链接跳转缓存、访问次数增量计数、短码不存在的负缓存和处理中批次临时存储。Redis 不是最终数据源，MySQL 仍保存短链接和已落库统计。

### 13. Redis 故障时还能跳转吗？

参考回答：

可以。Redis 查询失败时回源 MySQL，Redis 写入失败不阻断有效短链接的 302 响应。访问事件发布失败也只记录告警，不让用户的跳转请求失败。这是缓存和消息链路的降级边界。

### 14. 什么是缓存穿透？项目如何处理？

参考回答：

不存在的短码如果每次都访问 MySQL，就是缓存穿透。当前实现对不存在的短码写入 30 秒负缓存，后续请求可以直接返回不存在；创建新短码时会主动清除对应负缓存，避免短时间内误判。

### 15. 为什么缓存中还要保存 status？

参考回答：

如果 Redis 只保存原始 URL，短链接被禁用或删除后，缓存仍可能允许跳转。当前缓存同时保存短链接 ID、目标地址和状态，只有 URL、ID 存在且状态为 ACTIVE 时才允许命中。

### 16. 缓存 ID 被污染怎么办？

参考回答：

读取缓存后转换 ID 时捕获 `NumberFormatException`，清理异常缓存并回源 MySQL，避免因为 Redis 中的脏数据直接返回 500。

### 17. Redis Key 为什么要增加环境前缀？

参考回答：

如果开发、测试和生产共用 Redis 实例，而 Key 都使用 `short-link:`，不同环境可能互相覆盖。生产环境应配置为类似 `short-link:dev:`、`short-link:test:` 的前缀。当前项目已记录该风险，但尚未作为实习项目必做项实现。

## 五、RabbitMQ 与统计可靠性

### 18. 为什么访问统计使用 RabbitMQ 异步处理？

参考回答：

跳转是高频、低延迟链路，不应同步写多张统计表。RabbitMQ 可以把访问事件从跳转请求中解耦，由消费者异步写入访问事件表和每日 PV 表，从而降低跳转延迟。

### 19. 如何防止消息重复消费？

参考回答：

每个访问事件有唯一 `eventId`，消费者先写入事件去重表，数据库主键保证同一个事件只能成功一次；只有首次插入成功时才增加每日 PV。因此当前语义是 at-least-once 投递加消费端幂等。

### 20. confirm、returns 和 mandatory 分别解决什么问题？

参考回答：

publisher confirm 用于确认消息是否到达 RabbitMQ；publisher returns 用于处理消息无法路由到队列的情况；mandatory 要求不可路由消息退回。当前还携带 `CorrelationData(eventId)`，方便日志定位。它们能提高可观测性，但不能替代 Outbox 持久化补偿。

### 21. RabbitMQ 宕机时会不会影响跳转？

参考回答：

当前发布器捕获 RabbitMQ 异常并记录告警，跳转请求仍然返回 302。因此用户体验优先保证，但这也意味着消息可靠性需要后续通过 Outbox 或补偿机制进一步增强。

### 22. 定时同步如何避免丢计数？

参考回答：

不能先简单执行 `getAndDelete` 再写 MySQL。当前通过 Redis Lua 脚本把待同步计数原子领取到 processing Key：MySQL 写入失败时重新合并回待同步 Key；短码不存在或计数格式错误时隔离保存；处理中 Key 超时后下一轮恢复。当前语义是 at-least-once，而不是 exactly-once。

### 23. `visitCount` 和每日 PV 为什么可能暂时不一致？

参考回答：

`visitCount` 依赖定时任务把 Redis 增量同步到 `short_link`，每日 PV 依赖 RabbitMQ 消费，因此两条异步链路的处理时间不同。短时间不一致是允许的，最终会在消息消费和同步任务完成后趋于一致。

### 24. 为什么没有直接实现 Outbox？

参考回答：

Outbox 可以把业务数据和待发送消息放在同一数据库事务中，再由后台可靠投递。当前项目是实习规模，先使用 confirm、returns、幂等事件和失败日志覆盖核心故障窗口；Outbox、自动重放和监控平台已作为生产演进方案记录，没有把半成品包装成已完成能力。

## 六、认证与安全

### 25. Access Token 和 Refresh Token 为什么分开？

参考回答：

Access Token 有效期较短，当前为 15 分钟，用于接口访问；Refresh Token 有效期较长，当前为 30 天，用于换取新的 Access Token。Refresh Token 每次使用后撤销旧令牌并生成新令牌，降低长期泄露风险。

### 26. Refresh Token 为什么只保存哈希？

参考回答：

数据库只保存 Refresh Token 的 SHA-256 哈希，客户端保存原始令牌。数据库泄露时，攻击者不能直接拿数据库字段当作可用令牌。

### 27. JWT 密钥应该如何管理？

参考回答：

密钥通过 `SHORT_LINK_JWT_SECRET` 环境变量注入，不能提交到 Git。当前启动时要求密钥至少 32 字节。生产环境还应使用密钥管理服务，并考虑密钥轮换。

### 28. 当前登录接口还有什么安全不足？

参考回答：

当前还没有实现登录失败次数、账号锁定和 IP 限流。生产环境可以使用 Redis 按账号和 IP 记录失败次数，增加渐进延迟和临时封禁，并配合告警。`manageToken` 兼容接口目前仍是历史遗留能力，生产迁移后应只保存哈希并下线旧统计接口。

## 七、数据库与 Flyway

### 29. 为什么使用 Flyway？

参考回答：

Flyway 把数据库结构变更纳入版本控制，应用启动时自动执行未应用的迁移，并通过 `flyway_schema_history` 记录版本和校验和，保证不同环境的结构演进可追踪、可复现。

### 30. 为什么不能直接修改已经执行过的 V3？

参考回答：

Flyway 会校验历史脚本的 checksum。直接修改已执行的 V3 可能导致校验失败，也会让其他环境无法复现历史状态。正确做法是保留 V3，新增 V5、V6 等迁移脚本完成后续调整。

### 31. V3 分步回填 `workspace_id` 有什么风险？

参考回答：

先加可空字段、再回填、最后改为非空，过程中存在中间状态，严格来说不是原子变更。当前数据库规模较小且迁移已执行，因此保留现状并记录风险；生产环境应使用维护窗口、预检查、失败恢复和分阶段发布方案。

### 32. keyword 前后模糊查询有什么性能问题？

参考回答：

`LIKE '%keyword%'` 通常无法使用普通 B-Tree 索引，数据量大后可能全表扫描。当前数据规模较小，先保证功能；规模增长后可改前缀搜索、全文索引或独立搜索服务，并用执行计划验证。

## 八、测试与复盘

### 33. 项目使用了哪些测试？

参考回答：

使用 JUnit、Mockito 和 Spring Boot Test。单元测试验证服务分支、缓存异常、消息发布和 SQL 契约；上下文或集成测试验证 Flyway、MySQL、JWT、RabbitMQ 和工作空间权限。慢速依赖环境的测试需要在本地服务启动后执行。

### 34. 你如何验证一个故障修复是真的有效？

参考回答：

采用 TDD：先写能复现问题的失败测试，再写最小修复，最后运行目标测试和编译验证。例如缓存 ID 污染、负缓存、RabbitMQ 发布失败、同步回队和已删除链接统计都增加了对应测试。

### 35. 哪些问题属于代码，哪些属于环境？

参考回答：

代码问题包括 SQL 条件缺失、缓存状态未校验、旧接口契约失效等；端口占用、MySQL/RabbitMQ/Redis 未启动、Maven 仓库权限和 Git 凭据属于环境问题。环境问题不通过修改业务代码掩盖，而是记录现象并给出明确处理命令。

## 九、开放性追问

### 36. 如果访问量增长到每天一亿，你会如何演进？

参考回答：

先基于压测确定 Redis、RabbitMQ、MySQL 的瓶颈，再考虑 Redis Cluster、RabbitMQ 分片或多消费者、统计表按时间分区、冷热数据分离、异步批量写入和读写分离。只有有真实指标后才决定拆分微服务，不能只根据想象扩容。

### 37. 这个项目最大的不足是什么？

参考回答：

当前仍缺少登录限流、管理凭证哈希迁移、Redis 环境隔离、时区统一、DLQ 自动重放、链路追踪、Prometheus 监控和高并发压测。这些问题已经记录在复盘文档中，当前项目优先保证核心链路可用和故障可解释。

### 38. 如果重新设计，你会优先改什么？

参考回答：

第一步会继续迁移并下线兼容统计接口，统一 JWT 和工作空间权限；第二步增加登录限流和管理凭证哈希；第三步根据真实流量增加 Outbox、DLQ 重放、环境 Key 隔离和监控，而不是一开始就实现所有生产组件。

## 十、面试回答原则

1. 先说明当前真实实现，再说明生产演进方案。
2. 不要把 at-least-once 说成 exactly-once。
3. 不要把单元测试说成完整生产压测。
4. 遇到暂未实现的能力，说明原因、风险和后续方案。
5. 每个技术选型都要能回答“为什么这样做”和“失败时怎么办”。
